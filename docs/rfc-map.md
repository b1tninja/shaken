Citation rules, in the order they most often get broken:

1. Cite the document. A secondary write-up is a lead, not a source.
2. A section number is cited only if that section was read in full.
3. Errata are checked at each milestone freeze, not once at the start.
4. Where a claim came from a body outside the RFC series, that body is named here.

Re-verify with the RFC library rather than memory: `info('RFCnnnn')` for current status, `errata('RFCnnnn')` for corrections, and `read('RFCnnnn', view='normative')` for the MUST and SHOULD statements that become obligation rows.

## Measured findings about the examples

None of the examples below is used as a positive test vector. Each is pinned by a test in `tests/test_rfc_findings.py`, and the tests fail if the RFC Editor corrects the text.

1. **RFC 8225 Appendix A**: the 64-octet signature does not verify (ES256 over `header.payload`, with the R and S halves and also the low-S form tried) under the public key of A.2, nor under the public key derived from the A.1 private key. A.1 and A.2 are not a key pair. Checked with the `cryptography` package, and earlier by the review with ctspy's pure-Python verifier. The header and payload encoding steps in the same appendix are correct. Not on the RFC Editor's errata list.
   Measured further: the A.2 public key is the key of the **sec. 7.1 example** (also printed in RFC 8224 sec. 4.1.1): that signature, `rq3pjT1h...ck7w`, verifies under A.2 over the payload with the string `iat`. So the keys and signatures of the RFC examples come from an earlier draft of the examples, and erratum 5985's corrected payload would no longer match its signature (also pinned, `test_rfc8225_section_7_1_signature_does_verify_under_the_a2_key_for_its_string_iat_payload`).
2. **RFC 8225 sec. 9.1**: the printed final deterministic JSON is not valid JSON (the `dest` object's closing brace is missing).
3. **RFC 8225 sec. 7.1 and RFC 8224 sec. 4.1.1**: the payload decodes with `"iat"` as a string (erratum 5985, reported).
4. **RFC 8588 sec. 6**: the payload is not valid JSON as printed (no commas after `attest` and `dest`) and has a string `iat` (erratum 6656).

## Test vectors this project owns

`tests/vectors.py` is generated by `tools/make_vectors.py` from a fixed test-only P-256 key: a SHAKEN token, a certificate carrying a TN Authorization List, and the extension's DER written by hand from RFC 8226 Appendix A (independently of `shaken/tnauth.py`). ES256 is deterministic (RFC 6979), so the token regenerates byte for byte. The token also verifies under PyJWT as an independent implementation (`test_pinned_vector_verifies_with_an_independent_library`, skipped when PyJWT is absent). PyJWT is Python, so this is not the non-Python interoperability evidence the publication checklist asks for.
